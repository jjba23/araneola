** What is a Web Crawler?
:PROPERTIES:
:CUSTOM_ID: what-is-a-web-crawler
:END:

A web crawler (also known as a spider or bot) is an automated software program that systematically browses the internet to discover and index content. Think of it as an automated explorer that scans and jumps from page to page finding, following and using hyperlinks.

Search engines like DuckDuckGo, Ecosia, Google and Bing use massive fleets of crawlers to continuously copy and index the entire web so you can find things instantly when you search.

** What is a Sitemap?
:PROPERTIES:
:CUSTOM_ID: what-is-a-sitemap
:END:
A sitemap is a file (typically written in XML format) that acts as a blueprint or master directory for a website. It explicitly lists all the important pages, videos, and files on a site, along with metadata about them (like when a page was last updated).

#+begin_src xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
   <url>
      <loc>http://www.example.com/</loc>
      <lastmod>2005-01-01</lastmod>
      <changefreq>monthly</changefreq>
      <priority>0.8</priority>
   </url>
</urlset>

#+end_src

Instead of making search engine bots blindly guess how your website is structured by clicking random links, you hand them a sitemap.

It tells search engines exactly where your content is, saving them time and ensures isolated or deeply buried pages (ones that don't have many internal links pointing to them) still get discovered and indexed.

For details on the format of the XML, see: https://www.sitemaps.org/protocol.html

** Usage
:PROPERTIES:
:CUSTOM_ID: usage
:END:

#+begin_src shell
araneola --url https://example.org/ --output sitemap.xml
#+end_src

Run =araneola --help= for the full list.  The options that matter most when
crawling a site you do not control:

- =--max-urls= and =--max-depth= bound the crawl.
- =--delay= keeps it polite; a robots.txt =Crawl-delay= is honoured on top.
- =--exclude= and =--include= take regular expressions matched against
  canonical URLs, so a search page or a pagination trap is never fetched.
- =--timeout= and =--retries= decide how patient it is with a slow or
  flaky host (timeouts, dropped connections, 429 and 5xx are retried with
  exponential backoff, =Retry-After= included).

What it refuses to do:

- leave the seed host (or, with =--include-subdomains=, its subdomains);
- fetch anything robots.txt disallows;
- list a page that asks not to be indexed, whether through
  =<meta name="robots" content="noindex">= or =X-Robots-Tag=;
- list the same page twice: =rel="canonical"= and redirects are folded
  into one URL;
- publish a half-written sitemap: files are written to =.tmp= and renamed
  when the crawl finishes, and past 50,000 URLs or 50 MB a sitemap index
  is written instead.

* Ways to install
:PROPERTIES:
:CUSTOM_ID: ways-to-install
:END:

/Four routes to the same 0.0.2, from the most automated to the most manual.  They all build the tag this README documents./

** From the Guix channel
:PROPERTIES:
:CUSTOM_ID: from-the-guix-channel
:END:
*GNU Guix* is the functional package manager this project is developed with: a build is a pure function of its inputs, so the same recipe gives the same result everywhere, and an upgrade that goes wrong can be rolled back.

The jointhefreeworld channel carries ~araneola~ at 0.0.2, so a checkout of the channel is enough — no package definition to write:

#+begin_src shell
git clone https://codeberg.org/jjba23/guix-jointhefreeworld.git
guix install -L ./guix-jointhefreeworld araneola
#+end_src

Add the channel to ~$HOME/.config/guix/channels.scm~ (the channel's README has the four lines) and a plain ~guix install araneola~ keeps working on every later ~guix pull~.

** From the Nix flake
:PROPERTIES:
:CUSTOM_ID: from-the-nix-flake
:END:
*Nix* offers the same declarative, reproducible model with its own language, its own store and a binary cache, and it is a natural fit if the rest of your machine is already described in Nix.

The jointhefreeworld flake builds this project with this repository's own expression, so the package cannot drift from the source:

#+begin_src shell
nix build github:jjba23/nix-jointhefreeworld#araneola
#+end_src

The same attribute is available as an overlay, so ~pkgs.jointhefreeworld.araneola~ works inside a NixOS or home-manager configuration too.

** As a container image
:PROPERTIES:
:CUSTOM_ID: as-a-container-image
:END:
*Podman or Docker* is the route that puts nothing on the host: the ~Dockerfile~ in this repository builds the project in a builder stage and copies only what it installed into a runtime stage, so the image is small and the host keeps its own toolchain untouched.

#+begin_src shell
podman build -t araneola .   # docker build -t araneola . also works
podman run --rm -it araneola
#+end_src

The image's entry point is Guile, with araneola on its load path, which makes it useful for a quick try and for reproducing a bug on a clean system.

** As a distribution package
:PROPERTIES:
:CUSTOM_ID: as-a-distribution-package
:END:
*Debian, openSUSE and Arch* each get the project through their own package manager.  Packaging lives in this repository under ~packaging/~ and is pinned to the same release tag, so the recipes and the sources they build are versioned together.

None of the three archives ships araneola yet, so these are recipes to build rather than packages to install from a mirror:

| Distribution   | Package    | How to build it                                                                     |
|----------------+------------+-------------------------------------------------------------------------------------|
| Debian, Ubuntu | ~araneola~ | copy ~packaging/debian~ to the repository root, then ~dpkg-buildpackage -us -uc -b~ |
| openSUSE       | ~araneola~ | ~osc build~ with ~packaging/opensuse~                                               |
| Arch           | ~araneola~ | ~makepkg -si~ in ~packaging/arch~                                                   |

Each recipe carries its own dependency list, so a missing library fails the build with its name rather than producing a package that cannot load.

** Which one?
:PROPERTIES:
:CUSTOM_ID: which-one
:END:
- *Guix* if you want the toolchain the project is tested with, and the ability to roll back a bad upgrade.
- *Nix* if the rest of your machine is already declarative; the flake pins nixpkgs and gives you a binary cache.
- *Container* if you only want to try the release, or reproduce a report on a machine that has nothing installed.
- *Distribution package* if you want the project managed by the same tool as the rest of your system, with its licence, manual page and launcher in the usual places.

* TODO: Scan images in page and add to Image sitemaps
:PROPERTIES:
:CUSTOM_ID: todo-scan-images-in-page-and-add-to-image-sitemaps
:END:

Image sitemaps are a way of telling Google about other images on your site, especially those that we might not otherwise find (such as images your site reaches with JavaScript code). You can create a separate image sitemap or add image sitemap tags to your existing sitemap; either approach is equally fine for Google.

Image sitemaps are based on generic sitemaps so the general sitemap best practices also apply to image sitemaps. We also recommend that you follow the general best practices for publishing images.

Example image sitemap
The following example shows a regular sitemap with image sitemap extension, with two <url> elements:

https://example.com/sample1.html, which contains two images
https://example.com/sample2.html, which contains one image

#+begin_src xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"
    xmlns:image="http://www.google.com/schemas/sitemap-image/1.1">
  <url>
    <loc>https://example.com/sample1.html</loc>
    <image:image>
      <image:loc>https://example.com/image.jpg</image:loc>
    </image:image>
    <image:image>
      <image:loc>https://example.com/photo.jpg</image:loc>
    </image:image>
  </url>
  <url>
    <loc>https://example.com/sample2.html</loc>
    <image:image>
      <image:loc>https://example.com/picture.jpg</image:loc>
    </image:image>
  </url>
</urlset>
#+end_src

Image sitemap reference
The image tags are defined in the Image Sitemaps namespace: http://www.google.com/schemas/sitemap-image/1.1

Required tags
<image:image>	Encloses all information about a single image. Each <url> tag can contain up to 1,000 <image:image> tags.
<image:loc>
The URL of the image.

In some cases, the image URL may not be on the same domain as your main site. This is fine, as long as you verify both domains in Search Console. If, for example, you use a content delivery network such as Google Sites to host your images, make sure that the hosting site is verified in Search Console. In addition, make sure that your robots.txt file doesn't disallow the crawling of any content you want indexed.

* Getting Started
:PROPERTIES:
:CUSTOM_ID: getting-started
:END:


The easiest way to run Araneola predictably is by using *GNU Guix*. This ensures all dependencies (such as Guile, guile-lib, guile-scriba) are locked to the correct revisions but feel free to use the source code at will.

The project is built primarily with Guix (though you may use the code as you please) and automation is done with [[https://codeberg.org/jjba23/maak][Maak]] , check the ~maak.scm~ file.

Maak is very recommended, but not necessary, all you need is the Guix package manager installed, and then you can run the program easily. But feel free to use the Scheme code at will.

#+begin_src bash
guix time-machine --channels=channels.scm -- shell -m manifest.scm --

env SCRIBA_LOGGER=color-console guile -L ./src -c '((@(araneola main) main))'

--resources ./resources --url jointhefreeworld.org
#+end_src

*** CLI Options
:PROPERTIES:
:CUSTOM_ID: cli-options
:END:

-  =-u, --url=: The target root domain to begin crawling (protocols will automatically default to =https://= if left unspecified).
-  =-r, --resources=: Specifies the path directory to look for local assets or configuration resources.

* On Reproducibility: Why GNU Guix?
:PROPERTIES:
:CUSTOM_ID: on-reproducibility-why-gnu-guix
:END:

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
